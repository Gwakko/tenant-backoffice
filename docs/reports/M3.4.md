## Deviations from the spec
1. `04` UC-B1 step 6 "UPDATE the key row (`operation_id`)": impossible, `idempotency_keys` has no UPDATE grant (M3.1, deliberate). The ids are generated first and the key row is inserted complete (`operation_id` or `transfer_id`), then the operation is inserted in the same transaction.
2. Balance rows are not created with the node (nothing in M2 does it). The repository creates the row lazily at the first lock; a read of a missing row is zero (`updatedAt` = node creation time). If M3.3 or the node use cases create the row at node creation, the lazy insert simply does nothing.
3. Time stamps are taken under the row lock (after `FOR UPDATE`), so `created_at` order on a node equals the order of balance changes. Ties at one microsecond are possible with a real clock (the test clock is strictly increasing): a ledger sequence or ordering by `balance_after` chain would remove it; not changed.
4. A transfer checks the limit of both nodes (the smaller wins), and `operations_enabled` / activity of both.
5. A transfer by an actor with a role but without the right on the source node is `forbidden` (the source is checked first), not `not_found`.
6. Deactivation of a node concurrent with an operation is not serialised (spec lock table: balance row only); the node is read without a lock.
