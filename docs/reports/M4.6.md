## Findings
### Defect 1 (fixed): `parentId` revealed the id of an ancestor above the access root
`backend/internal/adapter/httpapi/dto_node.go`, `GET /nodes/{id}` (and every `Node` answer: create, rename, move, ...).
- Reproduction before the fix: the viewer of `A1u1` calls `GET /nodes/{A1u1}`. Answer: `"breadcrumbs":[{"id":"<A1u1>"}...],"parentId":"<A1 id>"`. `A1` is above the viewer's access root and is a missing node for the viewer (404). Test: `TestHTTPDescendantRoleDoesNotSeeAncestor/viewer_of_a_unit`: `should not contain "01a21e03-068a-7918-bdc0-353ca002cffe"`. Spec 03: breadcrumbs start at the access root, "предки вне поддерева не раскрываются"; EC-30.
- Fix: `parentId` is set only when the breadcrumbs hold the parent (`len(v.Breadcrumbs) > 1`); for an access root it is `null` (the contract already says `nullable: true`). One line plus a comment.
- After the fix: the test is green; reverting the line makes it red again (mutation k below). `make test-api` and the whole `make ci` are green: no existing test relied on `parentId` of an access root.
- Impact for M5: the web tree must not rely on `parentId` of an access root (use the access roots of `/me` and the breadcrumbs).

### 2. Cursors of nodes and members are bound at HTTP level (the M2.7 and spec note is outdated)
The task asked to record that these cursors carry only a position. At the use case level that is true (M2.7). Over HTTP the adapter signs and binds them (`handlers_nodes.go`, `handlers_members.go`: `CursorBinding{Scope: list kind + ":" + node id, Filters: ...}`): the binding is the list kind, the node id and the filters, NOT the reader. Observed matrix (probe, all asked as admin A): a cursor of `children` of B1 on children of A1, A, a missing node, any members list, any other list kind = 400 `invalid_cursor` (also for a foreign node: same answer as a missing one; garbage cursor too); a cursor of the very list of B1 on B1 = 404 (the position is valid, the scope is decided again: the reader has no access); a cursor of A1 children used by another reader with access (Multi) = 200, by a reader without access (admin B) = 404, equal to missing. So a foreign cursor opens nothing, and the strict 400 exists for nodes and members as well, not only for operations and audit. Remark: a cursor issued for B1 and used on B1 by a stranger is 404 while the same cursor on a random id is 400; the only people who hold a valid cursor for B1 had access to it, and cursors are signed, so this is not an enumeration vector.

### 3. Mutation (g) first escaped, test added
The first draft did not catch "audit with `nodeId` outside the scope returns an empty page": for a foreign or missing `nodeId` the 404 is produced earlier (`IsInSubtree` fails under RLS), and the `!inside` branch is reachable only for a node the reader SEES but that lies outside the scope (Multi views B1). Added `requireOutsideScopeLikeMissing` (audit and operations) in T-ISO-07 and T-ISO-08. Now caught (below).

### 4. Layers back each other up (as in M2.7)
Mutation (f): without the `balance.transfer` check on the destination, a transfer from A to a node of B still answers 404 (RLS hides the destination in the balance lock), so the pure foreign case does not catch it; the only case that pins the use case layer is the node the actor sees read-only (Multi, viewer of B1: must be 403, mutation gives 201).

Limit that must be said: the foreign and the missing nodes go through exactly the same code (the use case cannot tell them apart under RLS), so a mutation that changes only the answer for a foreign node cannot be written without a bypass of RLS. (a), (b), (c) are therefore per-route mutations; (b) and (c) are caught because `requireHTTPNotFound` pins the canonical 404 body and the exact header set (the equality of foreign and missing alone would pass them). The foreign-versus-missing equality therefore guards against a future RLS bypass or an owner-side lookup, which no mutation of the current code can emulate.
