- Security (the database does not check role x action, so the use case is the only guard):
  - `member.manage` is checked through `authz.Require` on every call; then `CanGrant(actorRole, new)` and `CanRevoke(actorRole, old)` with the actor's effective role (inherited ones included). Only an owner grants or removes owner; admin gets `role_not_grantable` (EC-33). The checks run before any write; a refused add creates no user.
  - Node outside the actor's subtree: `not_found`; inside, without the right: `forbidden`. A role on a descendant gives nothing on the ancestor.
  - Last owner (EC-35/36/37): the spec limits it to the ROOT node (non-root may lose its last owner, EC-37), so the guard works for the root only. It covers three paths: removal, `ChangeMemberRole`, and `AddMember` replacing the role of an existing owner (a hole the spec does not mention: demotion through POST). The guard locks the active owner rows of the root (`SELECT ... FOR UPDATE OF ra ORDER BY user_id`) in the same transaction as the write; the active owners other than the target must be at least one.
  - Whether the node is the root is read right after authorization and before any lock (see "Concurrency note").
  - `AddMember` creating a user: the id comes from `IDGen`; `users` is never read after the insert (no RETURNING); user first, then the assignment, one transaction; the hash comes from `user.Hasher` before `InTx`, only when a password was sent, and also when the user exists (the password is then ignored, so the cost does not reveal the email). The password and the hash are not logged, not returned, not put into audit or error texts (tests check this). A new and an existing user get the same `Member` shape; the only difference the spec requires is `validation_failed` for a new user without a password and `user_inactive`.
  - Same role again is a no-op (EC-40: no write, no audit, the stored `GrantedAt` comes back); another role replaces; one row per (user, node) by the primary key plus `ON CONFLICT DO NOTHING` and a reread for a concurrent insert.
  - Demotion or removal during a live session: no `token_version++`, as in the spec (Р-09: rights are read from the database on every request; `token_version` changes only on password change and user deactivation). The next request of the demoted user sees the new role; for removal the node becomes `not_found` (EC-42).
  - Audit through `AuditWriter` in the same transaction: `user.created` (`after.email`), `member.granted`, `member.changed` (before/after role), `member.revoked`. No entry for refusals or no-ops.

## Deviations from the spec
1. UC-M1 says `INSERT ... ON CONFLICT (email) DO NOTHING RETURNING id`. Checked in PostgreSQL 18: `ON CONFLICT` (also `DO NOTHING`) makes the new row pass the SELECT policy of `users`, and a new user is invisible to its creator until the assignment exists, so the statement fails with 42501. Implemented: `tb_user_id_by_email` first; if absent, a plain `INSERT` in a savepoint (nested pgx transaction); unique violation on `users_email` means someone else created it, the savepoint is rolled back and the id is looked up again (EC-109). Without a savepoint the failed statement would abort the whole transaction.
2. UC-M1 "user `inactive` -> `user_inactive`" before the upsert: the status of a user of another branch cannot be read before the assignment exists (RLS). Implemented: the assignment is inserted, then `users.status` is read (visible now); an inactive user gives `user_inactive` and the transaction rolls back (nothing remains, checked on the real DB). Same result as the spec, different order inside the transaction.
3. UC-M3: the audit entry is written BEFORE the delete. An actor removing their own last assignment loses sight of the node, and an audit insert after the delete would be refused by RLS once `audit_log` exists (M3.3).
4. UC-M3/M2: a missing assignment on the node is `not_found` (the spec says so for PUT; `03_api` lists no 404 for DELETE, I kept it consistent). `CanRevoke`/`CanGrant` refusals in remove and change give `role_not_grantable` (403, EC-33).
5. EC-36 outcome: the second remover is refused with `last_root_owner`, as the spec says. The reason, as seen in the first run: if the waiting actor was the owner removed by the first transaction, the node is no longer readable for them, which gave `not_found` from the repository. Fixed by reading the root flag before locking; after the lock the owner list (filtered by RLS) shows no other owner, so the answer is `last_root_owner`. The actor's role is deliberately NOT rechecked after the lock (a recheck would turn the EC-36 answer into `not_found`).
6. `port.Member` and `MemberRepo.GetForUpdate` return the email together with the assignment (needed for the output of change/remove paths); `MemberRepo.Insert` reports `inserted=false` instead of an error on a concurrent insert.
7. `ListMembers` returns `Item{Member, InheritedFrom *node.ID}`; ordering is (email, user id, node id), cursor is opaque base64.
