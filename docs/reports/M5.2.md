# Report M5.2: session, API client, login

## Done
- `web/src/api/client.ts`: `createApiClient({ baseUrl?, session, fetch? })` returns `{ client, refreshSession }`. The client does not import React or `auth` (layer rules); it gets a `SessionPort` (`getAccessToken`, `onTokens`, `onSessionLost`). Middleware: Bearer read from memory on every request; `credentials: 'include'` only for `/auth/*` (default `omit`); `X-TB-CSRF: 1` on `/auth/refresh` and `/auth/logout`; `X-Request-Id` (UUID) on every request. On 401 `token_expired`/`token_invalid` (not on login/refresh): exactly one refresh (single-flight: parallel requests await the same promise), then one retry of a clone of the original request (same body, same `X-Request-Id`, new token). The retry bypasses the middleware, so a second 401 is final (no second refresh, no loop). A request whose 401 arrives after another request already refreshed (token in memory differs from the one it sent) retries with the new token without a second refresh; if the session was lost meanwhile it is not retried. Refresh failed (any reason, including network): the session is reported lost once per flight, the original 401 is returned, nothing is retried.
- `web/src/api/problem.ts`: `parseProblem` (zod-checked `problem+json` body), exhaustive `problemMessages: Record<ErrorCode, string>` (a new contract code breaks the build until it has a text), `describeProblem` (dictionary, unknown code -> sanitised `detail` (control chars dropped, 200 chars), 429 with `Retry-After` seconds or HTTP date, 503 and network texts), `parseRetryAfter`, `networkProblem`.
- `web/src/auth/`: `session.ts` (token in a module variable; the React snapshot carries only `authenticated` and `user`, never the token; loss listeners), `useSession.ts`, `service.ts` (`sessionPort`, `ensureSession`: one restore attempt through the cookie per page load; `login`; `logout`: POST then clear memory and the Query cache even if the network fails), `guard.ts` (`requireSession` for `beforeLoad`), `wire.ts` (`wireSessionLoss`: clear Query cache, navigate to `/login?redirect=`), `redirect.ts` (`safeRedirect`, `loginSearch`).
- Open redirect: `safeRedirect` accepts only a path that starts with one `/` (not `//`, no backslash, no control chars or spaces, <= 512 chars), checks the raw value and up to 3 decoded forms, parses it against a placeholder origin and requires the same origin, never returns `/login*`; everything else becomes `/`. The login route uses it for the target, the guard and the loss handler use it when writing the parameter.

## Not done / limitations
- Sign-out in other tabs (BroadcastChannel) is not implemented: other tabs keep their in-memory token until it expires (10 min) and then fail the refresh (cookie revoked) and go to `/login`.
- Refresh failure for any reason (also 503/network) ends the session in the UI; a reload retries through the cookie. Chosen to follow `06` section 5 literally.
- Logout on an expired access token goes through the normal refresh-then-retry path (so the family is revoked); if the refresh fails the cookie stays until it expires.
- `/nodes/*` routes do not exist yet; the guard is `requireSession(api, href)` and is ready for them (M5.3+). `index.tsx` is still a placeholder (no redirect to the first access root).
- Real browser and cookie behaviour (HttpOnly, SameSite, nginx proxy of `Set-Cookie`) is not covered by unit tests; MSW does not emulate the backend rejecting a missing CSRF header (that is T-A-33 in Go).
