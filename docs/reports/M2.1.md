## SECURITY DEFINER functions
| Function | Reads bypassing RLS | Returns | Why it is not a leak |
|---|---|---|---|
| `tb_actor_scopes()` | `role_assignments`, `nodes`, `users` filtered by `user_id = tb_actor_id()` and active user | `ltree[]`: paths of the actor's own assignments | the actor id comes from the session setting, not an argument; the paths are the actor's own scopes; empty array without actor |
| `tb_auth_user_by_email(p_email)` | `users` by email | `id, password_hash, status, token_version` of at most one user | needed before an actor exists; one exact-match row (no pattern, `lower()` of input); exposes a hash only to whoever knows the email, as login requires. Residual: a compromised app can obtain any known user's hash, which a login flow cannot avoid |
| `tb_auth_user_by_id(p_id)` | `users` by id | same four columns | called with the verified token subject; exact match; same residual |
| `tb_user_id_by_email(p_email)` | `users` by email | a uuid or NULL | NULL unless the actor holds a role somewhere (`cardinality(tb_actor_scopes()) > 0`); returns only the id. Residual by design (EC-109): an authorised actor learns that an email exists |
| `tb_node_effective_active(p_node_id)` | `nodes` including ancestors above the access root | boolean or NULL | NULL unless the node is inside the actor's scopes (checked by `path <@ tb_actor_scopes()`); only one boolean about ancestors is revealed (the status of hidden ancestors, required by EC-18/20) |

Common: owner `tb_owner` (migrations run as it; on a roundtrip as superuser), `SET search_path = pg_catalog, public, pg_temp`, `REVOKE ALL ... FROM PUBLIC`, `EXECUTE` to `tb_app` only, plain `LANGUAGE sql`, no dynamic SQL. `tb_actor_id()` is not SECURITY DEFINER (`search_path = pg_catalog, pg_temp`, EXECUTE to `tb_app`).

## Deviations from the spec
- No `FORCE ROW LEVEL SECURITY`: `02` section 5.2 explicitly says without FORCE (the owner `tb_owner` must bypass RLS for migrations, seed and the DEFINER functions). `tb_app` is always subject to policies. A test asserts `relforcerowsecurity = false` so a change would be deliberate.
- `search_path = pg_catalog, public, pg_temp` instead of `public, pg_temp` (pg_catalog first, pg_temp last).
- `users` INSERT policy: `cardinality((SELECT tb_actor_scopes())) > 0` instead of `true`, so a session without actor cannot create users (EC-57 requires INSERT to fail with 42501 on all tenant tables).
- `role_assignments` SELECT policy: own rows only while the actor has scopes (an inactive user sees nothing). UPDATE/DELETE use the node-visibility predicate, as in the spec table.
- `tb_user_id_by_email` returns NULL without an acting role-holder (spec: unconditional).
- Column grants (stricter than the spec): `tb_app` cannot read `users.password_hash` (`SELECT *` on `users` fails with 42501; login goes through `tb_auth_user_by_*`); no DELETE on `users`; on `refresh_tokens` only `used_at` and `revoked_at` are updatable, `token_hash` is not.
- `refresh_tokens` has no RLS (spec); only grants are set.
- The task text lists the functions under 0002; the spec places them in 0003 (done there).

## Notes for next milestones
- `INSERT INTO users ... RETURNING` fails under RLS (a new user is invisible until assigned, SELECT policy applies to RETURNING): `UserRepo.InsertIfAbsent` (M2.3) must generate the id in the app and use the row count plus `tb_user_id_by_email`, not `RETURNING` (test `insert user without RETURNING ...` documents it).
- `INSERT INTO nodes` under a foreign parent fails with `23514` (parent trigger reads the parent under RLS) before RLS gives `42501`; the adapter must map both to not found.
- An actor with UPDATE rights can change `password_hash`/`status` of any user visible in their branch (the policy cannot distinguish columns); use case line 1 must restrict this. A user who also belongs to another branch is affected globally (status, password).
- FK checks bypass RLS: an assignment for a user that exists elsewhere succeeds, a missing user gives 23503 (existence oracle by id, same class as EC-109).
- `set_config('app.actor_id')` can be called by any code running as `tb_app`: the actor is trusted input of the app (SQL injection with arbitrary statements would defeat RLS; parameterised queries only).
- `.golangci.yml` has no `build-tags`, so `lint-go` skips `integration` files. Checked by hand: `golangci-lint run --build-tags integration ./internal/isolation/...` gives 0 issues; the same run flags a pre-existing `contextcheck` in `internal/testkit/db_test.go:22` (not touched).
